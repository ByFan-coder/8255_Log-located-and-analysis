# T18D（8255）日志定位与问题分析

目标：默认从当前目录及其子目录找到实际日志，确认故障所在层、最早可见异常、影响链和缺失证据，输出可复核的分析及截图位置。用户明确指定子目录时以该目录为分析范围。

## 适用范围与历史依据

- 不依赖固定盘符、项目根目录或历史文件夹名称；只从本次当前目录发现日志入口，不自动向其他工程目录扩展搜索。
- T18D 历史案例有 QNX/Android 日志；EHV 关联案例有 Linux PVM/Android Guest。先从当前包的文件、版本及启动信息确认架构，再选分析路径。不要把 EHV 的内核版本、模块实现、服务配置或故障结论当成 T18D 的既定事实。
- [历史案例与证据边界](references/history.md)记录来源聊天及后续修正。它用于形成排查假设；当前问题的结论必须回到当前原始材料验证。

## 执行流程

### 1. 首先确认故障时间与分析边界

提取用户描述、图片中的故障日期、时间或时间段、时间来源（录像/照片、测试记录、设备显示、日志），以及物理屏、操作前提、恢复方式和软件版本。区分实际发生时间、发现/报障时间及人工重启时间；核对时区和影像设备与日志的时钟偏差。将用户明确排除的测试重启、手动操作和已否定方向记入分析约束。

**时间与覆盖检查是进入原因分析前的首要步骤，适用于完整分析和简析。**故障时间不明或互相矛盾时，先询问用户故障发生日期、时间段及时间来源，同时可以继续日志清点、启动/校时和覆盖检查；不能任意挑选一个异常当成本次故障并定责。若当前材料只能建立候选窗口，明确标记为未确认。

用户只给目录名时，在当前目录及其子目录定位；存在多个候选时列出候选和各自日期，避免混入同名旧包。未找到则说明本目录缺失的材料，不转去历史工程路径。优先读取适用的 AGENTS.md。

### 2. 清点日志并初查时间范围

先读[日志目录与格式](references/log-map.md)。用 `rg --files --hidden` 枚举，再检查顶层目录、文件大小、文件头、日期范围及轮转编号；发现遗漏时再针对性使用 `--no-ignore`。不要第一次就对全部大包执行全文搜索。

为目标目录生成简洁清单：

`原始路径 | 系统归属 | 格式 | boot/启动段 | 原始时间范围 | 已核实连续区间/缺口 | 故障前/中/后覆盖 | 解码/解压状态`

默认优先级如下；用户明确要求分析其他日志时，按用户要求调整：

1. **先看 `qnxlog` 下的 `slog2` 与 `systeminfo`**，包括名称变体、轮转文件和压缩分片。两者结合定位故障时序、进程/线程状态、CPU、内存及驱动异常，不只看报错摘录或 CPU 排行榜。
2. **检查当前目录中的 `QNXRunInfo.tar.gz`**。先列成员，再按 bug 需要提取 QNX 驱动相关信息、运行状态或配置，补充 slog2/systeminfo 的证据。实际内容以包内清单为准，不假设每包都有相同快照或故障现场。
3. 根据故障链再关联当前目录中的 Android、适用版本 PVM Linux、core、ANR、pstore 等日志。`qnxlog` 不存在时，在本目录其他子目录寻找 slog2/systeminfo 等同类文件，不因缺少固定目录名停止分析。

优先找完整系统日志及故障前后的相邻分片，再查已生成的 analysis 报告作为线索。无扩展名的编号文件同样可能是关键文本。

按魔数识别压缩或封装。普通 gzip 可流式读取或解压；`DSV_PKMS` 需要匹配的解封工具。压缩包截断、解码失败和缺分片要列入覆盖限制，不能将未读成功的内容记作“没有异常”。原始包保留；派生文件写入本次独立分析目录，保留来源映射。

### 3. 完成时间对齐、日志覆盖与缺失检查

分别标记 QNX、Host、Guest 的启动边界、PID 生命周期、日志轮转、校时和 suspend/resume。1970/2000/2192 等异常日期先作为时钟状态线索，不因日期奇怪丢弃该段。

- 文件名日期及导出时间不等于事件时间。
- Host boot ID 相同仍不能证明 Guest 未重启；需单独识别 Guest 实例。
- 同 PID 在不同 boot 中不代表同一进程。
- 跨端优先匹配唯一事务、Guest PID 与进程名的握手/断开、相同消息载荷或带 Host 接收时间的 Guest console；最好用第二锚点复核。
- 只有同一连续时钟段才做 `T目标 = T锚点 + (t目标 − t锚点)`；注明时钟域、偏移来源和误差。跨休眠或校时重新找锚点。
- UART 与 Android 内核格式化墙钟的对应，不自动等于 Host 与 Guest 对齐。缺共同锚点时保留候选窗口，不能据此排除 Host 日志覆盖。

跨端或休眠问题需要更精确对齐时，读[时间对齐方法](references/time-alignment.md)。

对每个与本次故障有关的日志源分别判断：**已覆盖、部分覆盖、未覆盖、无法确认**。优先核对 qnxlog 的 slog2、systeminfo 和 QNXRunInfo，再核对当前故障链需要的 Android/Host 等日志；未获准的 display_log 仍不得解析，覆盖记为“无法确认/待授权”，不能为覆盖检查绕过询问规则。

- 检查故障前、发生时、发生后三个阶段是否都有相关记录，记录具体覆盖区间和缺口；故障后启动的日志或快照不能补作故障瞬间证据。
- 不只比较首末时间。核对分片之间与文件内部的时间跳变、校时、重启、轮转、截断、丢日志提示和解码失败，避免首末时间包住故障、实际中间却有缺口。编号跳跃和长时间无打印只是疑似缺口，需结合轮转规则、采集方式和其他源验证，不能单凭它们断言丢日志。
- systeminfo、QNXRunInfo 等可能是周期/单次快照，分别给采样点及间隔；采样间无记录不直接认定为日志丢失，也不能声称覆盖了间隔中的故障瞬间。
- 明确区分“日志未采集/未导出/损坏/未解码/时钟未对齐”和“已核实覆盖内未发现相关记录”，不把任何未覆盖或未读成功的部分用于排除模块。

**完成此检查后，先向用户简要说明故障时间、各源覆盖状态和已知缺口，再进入后续定位。**已覆盖或部分覆盖时，只分析有证据支持的阶段并注明限制；关键故障窗口未覆盖、时间无法确认或两端尚未对齐时，优先给出具体需补齐的日志源、日期/boot和时间窗口，必要时请求时间锚点。可继续独立分析已覆盖记录，但不能声称已定位本次根因、首次触发或已排除缺失阶段的模块。最早可见异常不能等同实际起点。

### 4. 从现象回溯到最早可见异常

只有在前述时间与覆盖检查完成并披露限制后，才开始按 bug 做关键词定位和原因推断。在 **slog2** 中根据 bug 情况优先选查 **`kgsl`、`smmu`、`openwfd`、`display`、`i2c`、`disp_svc`、`ads_service`**，关键词不区分大小写。按[分支排查](references/diagnosis.md)的关键词表选择起点，再展开上下文和相邻模块，不把全部关键词命中数作为故障结论。

先圈定故障前后约 2～3 分钟，再按异常起点、初始化阶段及更早趋势扩展。窗口应随现象调整，不能因固定窗口错过长期耗尽或建通道等待。

根据[分支排查](references/diagnosis.md)选择相关链路。搜索保留时间、进程、PID/TID、屏/端口/显示 ID、请求及返回值。粗筛命中后读取上下文，不把单独 `error`、`timeout`、`0xNN` 当成故障证明。

**屏端分支：**如果现象或主机日志提示可能是屏端问题，例如背光/屏端通信异常、触摸原始帧异常、面板复位或局部掉电，先检查当前目录有无 `display_log`。找到时先询问用户：“当前现象可能涉及屏端，是否需要继续解析当前目录下的屏端日志 `display_log`？”说明需要核对的具体问题；收到同意前不解析其内容，继续独立的 slog2/systeminfo 分析。用户已明确要求解析该日志时直接执行，无需重复询问。未找到时说明缺少屏端日志，不假定已排除屏端问题。

**未定位时必须扩展到其他层级。**QNX与屏端日志查不到足以解释故障的证据时，不能停在“没有异常”或只让用户补屏幕日志。按[跨层级继续排查](references/diagnosis.md)根据现象主动检查当前目录中相关的应用、fwk、Android内核、图形合成/HAL、启动服务/开机动画、业务通信及适用构建的Host/PVM日志；每新增一类先核实时间、启动关联与覆盖，再追踪同一事件的上下游。QNX内核/驱动未定位时，也应检查QNX上的仪表应用、窗口管理、业务与进程管理等软件层，不能把QNX整个系统当成单一驱动层。

“覆盖内未发现足以解释故障的记录”不等于“该层已排除”；覆盖缺失、未解码或display_log尚未获准时，说明限制并继续其他可独立检查的层级，不将屏端解析当成继续排查的前提。当前目录没有所需的其他层日志时，明确需补的日志种类、目标进程/模块及故障时间窗口；相关可用材料均检查后仍无法定位，就报告已查范围和下一步最有价值的补采，不编造模块归属或根因。只有证据实际转向非驱动、非屏端软件层，才使用简析与流转模块格式；仍考虑屏端时保留对应故障屏的信息与现场核对要求。

建立时间线，区分：用户报障时刻、最后业务输出、最早可见异常、崩溃/ANR、窗口消失、重启、恢复。最早可见异常受日志覆盖限制，不一定是实际故障起点。核对故障前正常窗口是否也有同类打印。

分析核心原则：

- **结论不武断。**明确区分“日志已确认的事实”“可能原因”“待确认的现场情况”。证据不足时给出与现有现象相符的可能原因、各自依据和验证办法，不直接定责、不把单条报错写成唯一根因，也不编造概率。候选应与本次证据相关，不为显得全面罗列无关故障。
- 请求不等于执行成功；背光设置返回值不等于屏端实际亮灭反馈。
- FPS、心跳或持续日志只能证明对应活动，不证明实体画面正确或所有业务正常。
- 等待者不等于持锁者；pending work 不等于正在执行；D 状态或高 load 不等于占满 CPU。
- 错误跨层传播可能对应同一次事件。分别报告匹配行数和可关联的独立事件数，不能直接累加。
- 日志未出现、完整进程快照中不存在、明确退出记录，是不同强度的证据。
- 现象相似不等于同根因，时间相邻不等于因果。

**现场核对：**当可能原因涉及线束接触、屏端供电/复位、背光、实体屏画面或其他需现场状态才能区分的情况时，必须询问用户是否有故障现场视频或照片，并说明需要核对的具体现象。例如：“当前日志显示向屏端发送 I²C 请求未收到 ACK，可能与通信线束/连接、屏端供电或复位状态有关，也需核对地址及透传配置。是否有故障时的现场视频或照片，可帮助核对屏幕实际表现、连接情况及故障发生前后的操作？”视频/照片只能确认可见现象；画面黑、连接器外观正常均不能单独证明供电异常或电气连接正常，必要时再建议电压、波形或链路测试。已提供相关影像时先核对其覆盖，无需重复索要；只询问仍缺的视角或时段。等待补充期间继续日志分析，保留暂定结论，不把未回复视为已确认。

### 5. 输出可复核结论

使用[分析输出模板](references/report-template.md)，先按当前证据选择输出分支，再按用户要求缩放篇幅。默认中文。驱动或屏端相关问题给出必要的时间线、关键证据、可能原因及验证建议；**非驱动且非屏端问题必须走简析分支**：用易懂语言简述发生了什么、可能卡在哪一步，只给最重要的几处日志定位，末尾输出 `建议流转模块/层级：xxxx`，例如 fwk、安卓内核、仪表应用、开机动画。不输出屏幕信息，也不输出“屏幕信息查找失败”。

简析时通常选 2～4 处关键证据，每处给实际日志路径、原始行号和一句解释，按证据需要增减，不凑数量；不展开无关的驱动链、寄存器及长篇日志。建议流转表示优先由谁继续分析，不表示根因或责任已经确认。若当前无法区分模块，保留不确定性，例如 `建议流转模块/层级：fwk 优先，仪表应用配合（具体归属待确认）`。仅因缺少驱动报错不能声称已排除驱动；仍有与故障相关的驱动/屏端疑点时保留相应分支。

每个关键判断附真实文件路径、**编辑器计行方式下的 1-based 行号**、原始时间和相关 PID/TID/显示通路。所有对外行号，包括截图范围、屏幕信息定位、报告与链接，都必须先转换并复核；不能直接采用搜索工具的行号。混合换行文件中，搜索工具与编辑器可能计行不同，不能套用固定偏移。默认将 CRLF 作为一次换行，独立 LF、独立 CR 也各计一次，保留空行；自动折行的显示行不增加文件行号。使用[编辑器行号定位工具](scripts/editor_line_locator.py)按唯一日志原文重定位，具体规则与用法见[日志目录与格式](references/log-map.md)。若用户指定编辑器的计行行为不同，以该编辑器为准并核对相邻原文；未验证一致时明确说明计行口径，不冒称已经在编辑器验证。gzip 行号注明“解压后、按编辑器换行规则计数”；过滤文件的行号不能充当原文件行号。

**屏幕信息必填规则：**每次分析结束后，只要仍考虑屏端问题，就在最终回复及保存的分析报告末尾按[输出模板](references/report-template.md)附上屏幕信息：`零件号：`、`软件/固件版本：`分开两行，每行结果后紧跟可点击的原始日志文件与行号定位。版本这一行必须完整列出 `hw_ver`（硬件版本）、`sw_ver`（软件版本）、`tp_ver`（触摸版本）、`supplier_code`（供应商代码），保留日志原始值，不能只输出 sw_ver。先从已允许读取的 slog2、systeminfo 和 QNXRunInfo 等材料检索；读取 display_log 仍遵守前述询问规则。查不到屏幕信息时显示原文“屏幕信息查找失败”，不以主机版本、屏型配置或历史案例填充。

**屏幕信息必须对应本次故障屏。**仪表问题给仪表屏的零件号和版本，吸顶屏问题给吸顶屏的零件号和版本，中控或其他屏同理；每组信息前明确标注屏幕名称。先用日志中的屏幕标识、通路、端口或初始化映射核实归属，不能直接取首次搜索命中的版本，尤其不能拿 `ivi_touch` 的中控信息替代仪表或吸顶屏信息。无法确认归属时标记目标屏的“屏幕信息查找失败”，不要以另一屏的信息代替；多屏故障分别输出，不跨屏拼接。非驱动、非屏端简析仍按既有规则只给流转模块，不输出屏幕信息。

驱动或屏端的完整分析通常保存 `分析报告.md`、`关键证据.md`；涉及多包/多 boot 时补 `日志清单.csv`。简析分支默认直接在聊天输出，不为填满完整模板另造长篇报告；用户要求保存时使用相同简析格式。用户只要截图时，优先给几处短行段和用途。若后续要求英文 Case，提供简洁英文标题、描述、附件索引；保留不同启动或不同案例的独立标签。需截取 2～3 分钟日志时，保留窗口内所有模块和多行记录，仅关键词摘录不能称完整窗口。对外提交由用户另行授权。

只有日志可证实故障机制且有匹配源码、dump 或验证闭环时才写“根因已确认”。否则明确写“已确认的故障点”和“根因待验证”，并给出需要补齐的具体文件、时间/boot、符号和验证目标。
