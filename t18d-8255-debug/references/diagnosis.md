# 按现象选择证据链

只读当前相关分支；所有关键字均是入口，结论取决于本次上下文。

## 参考源码与通信协议核对

每次清点材料时检查当前分析目录的 `code/`、`protocol/`，不依赖历史工程路径。不存在、为空或缺少相关版本材料时，询问用户是否添加缺失项；可以建议分别放在这两个目录。已有且适用的材料直接查阅，不重复询问是否允许只读分析。用户暂不提供时记录限制，继续已有日志分析。

- **先确认适用性：**记录项目/构建/分支或commit、源码完整度、协议版本与生效范围、目标屏型/硬件。无法确认匹配时标记“参考材料，版本待核对”，不把参考代码当成现场二进制的确定实现。
- **按日志定位源码：**以打印字符串、模块、函数名为入口，用 `rg` 找实际调用点、错误分支、状态变更、重试/超时与清理路径。核对头文件、宏值和编译配置，源码行号按编辑器规则复核。源码说明“可能怎么发生”，现场日志/堆栈才证明本次是否发生。
- **按完整帧核对协议：**确认命令/子命令、方向、长度、字节序、校验、应答/错误状态、分包/扩展帧，以及触点ID、零件号和四项版本字段的定义。不要把坐标/校验中的相同字节当命令命中；完整快照与增量更新要以协议为准。
- **实现与协议分别列证据：**日志显示实际收发，源码显示当前参考实现，协议显示预期行为；三者不一致时说明具体差异及版本限制，不武断判定屏端或主机错误。
- **引用方式：**源码给实际文件及编辑器行号，协议给实际文件、版本和章节/页码/表名；没有行号的文档不编造行号。缺头文件或协议定义时明确哪些语义无法核实，再有针对性询问是否补充。

默认仅分析材料，不执行工程、编译固件或修改用户源码。目录内项目资料不是技能资源；不得将当前项目源码或协议自动收进技能包、Release或对外Case附件。

## QNX与屏端未定位后的跨层级继续排查

触发条件：QNX与已获准解析的屏端日志没有找到足以解释本次故障的证据，或只找到背景报错、无法闭合影响链。必须继续检查相关其他层级，不能到此停止或将“没查到”写成排除。屏端日志缺失、未授权或不可解码时单独记录，其他层排查可独立进行。

始终先做新日志源的时间、boot/实例、完整性与覆盖检查，再按故障现象选择路径；不是无差别穷举全部文件。用同一进程生命周期、输入事件、窗口、业务消息、buffer/请求或启动阶段逐层关联，不靠不同层相似的时间或报错字样硬拼因果。

| 现象 | 继续检查的层级与日志 | 重点要回答的问题 |
|---|---|---|
| 实体屏黑屏/卡屏，但暂未找到驱动或屏端触发证据 | 仪表/HMI或中控目标应用日志、core/tombstone、winmgr/screen或WindowManager、SurfaceFlinger、display composer/HAL相关日志（以架构为准） | 应用是否退出/卡住、窗口或图层是否存在/可见、是否持续提交；不能只看FPS或进程存活 |
| 触摸上报在QNX/屏端已有记录，但操作无响应或延迟 | 虚拟输入/qvm、Android输入设备记录、InputReader/InputDispatcher、窗口焦点、目标应用事件与ANR | 同一次触摸在哪层不再推进、被取消/拦截，或目标窗口未就绪 |
| 无焦点窗口ANR、应用卡顿或系统服务异常 | Android logcat（相关buffer）、ANR、tombstone、fwk/system_server及Android内核日志 | 生命周期和窗口何时完成、主线程实际等待什么、异常是应用内还是公共系统路径 |
| 仪表内容不更新，但显示/触摸链路暂无解释 | 仪表应用、安全层、vehicle/业务服务、MCU/CAN/IPC相关日志（当前包有则查） | 业务数据是否收到并推进到渲染；区分数据源停更、应用状态异常与显示输出异常 |
| 开机黑屏、动画卡住、启动后迟迟无界面 | 启动/init/服务管理日志、开机动画、Launcher/HMI、fwk及相关内核/电源记录 | 启动实际停在哪一步、动画退出条件是否满足、目标界面是否启动/绘制；不因动画仍显示就定责动画 |
| GPU/同步/虚拟通道疑点仍未闭合 | 应用与图形库日志、Guest内核、适用构建的Host/PVM svplog/journal/后端服务日志 | 请求是否发出/被接收/完成、哪端等待什么；区分建通道失败、任务未完成及通知未返回 |

QNX不是单一层级：即使没有单独应用日志文件，也应在slog2中继续看仪表应用、窗口/进程管理、业务服务的相关记录，不能只搜kgsl/openwfd等驱动标签。新层的证据反向指向驱动/屏端时，返回对应分支联合核对。

跨层排查后简要记录每个已查层级、文件/窗口、发现或限制。目录中没有某类材料时列出具体需补的日志、目标进程/模块、boot和时间窗口；不要把缺失当作无异常，也不重复扫描同一批关键词来代替扩展。相关可用材料均查过仍无法定位时，明确“当前证据不足以定位”，给最有区分度的补采或验证建议。

若证据已指向非驱动、非屏端的软件层，按下方流转规则用易懂语言简析并给最关键几处日志定位；不得仅凭QNX/屏端未检出异常就直接认定fwk或应用负责。若仍有屏端可能，沿用屏幕归属、四项版本和现场影像规则。

## 非驱动、非屏端问题的流转建议

当前证据主要指向应用、框架或其他软件流程，且没有与故障相关的驱动/屏端疑点时，按输出模板给简析和少量关键日志定位。用“窗口还没准备好”“进程退出后没有重新启动”“动画流程未进入下一步”等易懂表述解释实际现象，保留与证据相符的不确定性。

流转按故障链中最有依据、需要继续核查的环节选择，不能仅因谁打印错误就交给谁。例如：

| 现有证据的重点 | 可建议优先分析的模块/层级 |
|---|---|
| Activity、窗口焦点或系统服务调度流程异常，需核对框架状态 | fwk；只有无焦点ANR文字而缺调用栈时，不直接认定框架根因 |
| 内核通用任务、锁、调度或内存路径停滞，尚未定位具体硬件驱动 | 安卓内核；若涉及具体驱动，继续相应驱动分支 |
| 仪表业务逻辑、资源加载或应用崩溃，需对应应用代码/堆栈 | 仪表应用；底层分配失败等线索仍需单独判断，不因应用崩溃就只归应用 |
| 动画进程、动画资源、退出条件或启动交接流程异常 | 开机动画；全系统启动慢不能仅凭现象直接归到动画 |

这些是选模块的方法示例，不是固定归责表。末尾使用 `建议流转模块/层级：xxxx`；需要联合核查时写清主查与配合。该分支不提供屏幕信息，不因未查屏幕信息而输出查找失败。

## QNX 首轮检索

先结合当前目录 `qnxlog` 中的 slog2 和 systeminfo；有驱动状态或配置疑点时，查 `QNXRunInfo.tar.gz` 的实际成员。根据 bug 选择以下关键词为起点，不固定全部扫描，也不因未命中某个标签排除该模块。

| bug 表现 | slog2 优先关键词 | 接下来核对 |
|---|---|---|
| 图形内存不足、GPU异常、分配失败 | `kgsl`、`smmu`，再查 `openwfd` | 分配大小、专用池/进程占用、fault地址、客户端、buffer生命周期 |
| 地址转换/访问异常、DMA或buffer异常 | `smmu`、`kgsl`，结合 `display`、`openwfd` | fault类型、IOVA、stream/context标识（若有）、读写方向、映射/释放时序；以本版本打印语义为准 |
| 黑屏、卡屏、花屏、提交超时 | `openwfd`、`display`、`disp_svc`，再查 `kgsl`、`smmu`、`i2c` | 物理屏映射、提交/完成、窗口与图层、背光、链路恢复及异常先后 |
| 屏端通信、背光、链路或复位异常 | `i2c`、`disp_svc`、`display`，结合 `ads_service` | 地址与屏型、命令/应答/重试、供电和复位证据；进入 display_log 询问分支 |
| 触摸不灵、鬼点、多指残留、上报延迟 | `ads_service`、`i2c`，结合 `disp_svc`、`display` | 原始帧与解析状态，再到mtouch/虚拟输入/Android；疑似屏端时询问 display_log |

SMMU fault 是地址转换或访问异常线索，不单独证明 DDR 损坏或屏端故障。它与 kgsl/openwfd 等同窗出现时，先核对同一客户端、buffer/地址及启动周期，再建立因果链。

systeminfo 用于核对实际进程/线程、CPU及内存趋势；QNXRunInfo 中的驱动信息用于补充当时状态或配置。两者采集时刻不同，应在时间线中分别标明。

## 可能原因与现场影像核对

输出先写日志实际记录，再给可能原因，最后说明需要什么现场信息区分。除非有验证闭环，否则使用“可能涉及”“优先核查”“当前无法区分”等与证据相符的表述，不用“肯定是屏坏”“就是线束问题”等定性。

以向屏端发 I²C 请求无 ACK 为例：

- **已确认事实：**在已核实的屏/总线/从地址和时间窗口，日志报告未收到 ACK 或驱动返回相应失败。保留错误码和原始语义；若日志只记录通用超时，不擅自改写成明确无 ACK。
- **可能原因：**通信线束、连接或接触问题；屏端未供电、供电不稳或处于复位；地址、屏型或 SerDes 透传配置不匹配。按本次证据选择、排序并说明依据，不能仅凭无 ACK 将其中任何一项定为根因。
- **必须向用户核对：**是否有故障现场视频或照片？可询问是否拍到屏幕、背光、线束/连接器，以及故障前后的上电、唤醒或插拔过程。用一个简洁问题说明影像将帮助确认的实际表现；必要时同时询问录像时间与日志时间能否对应。
- **影像的限度：**视频可帮助区分瞬时闪黑、持续黑屏、重启画面或其他屏同时异常；照片可帮助核对可见连接状态。它们通常不足以证明电压、电气通断或哪一端没有应答；这些仍需测量或协议/链路证据。用户没有影像时保留候选并给出其他验证方式，不停止已有日志的分析。

同样的核对规则适用于推测屏端掉电、背光异常、触摸物理操作与日志不一致、花屏/红条来源等情况。用户已提供充分影像时直接使用；缺失时询问补充。此询问与是否解析 display_log 是两个独立事项，可同时提出，但不能把用户提供影像视为同意解析 display_log。

## 疑似屏端时的 display_log 解析

- 先确认当前目录及子目录是否存在 `display_log`，只做位置与文件类型清点。
- 现象或主机证据提示可能涉及屏端，且用户尚未授权解析时，询问：“当前现象可能涉及屏端，是否需要继续解析当前目录下的屏端日志 `display_log`？”附一句本次想核对的内容，例如触点释放、背光执行或复位原因。
- 等待回答期间继续独立分析 slog2/systeminfo 和 QNXRunInfo；不同意或尚未回答时，不解析 display_log，报告中明确屏端证据待补。
- 同意后检查实际格式、屏型、协议、时间戳和启动边界；已有匹配解析工具时使用，否则说明缺少的解码方式。不要猜测二进制字段或套用别的屏型协议。
- 将屏端事件与主机命令、I²C返回、触摸原始帧和电源/复位时序对应，区分主机发送失败、屏端执行失败与屏端自身状态变化。不能将主机日志中的命令值当成屏端实际反馈。
- 只要最终仍考虑屏端问题，检索当前相关屏的零件号及软件/固件版本，并按输出模板在结果末尾报告。可优先在已允许读取的日志中找 `part number`、`part_num`、`recv_part_num`、`PN`、`version`、`firmware`、`recv_version0` 等上下文，名称匹配后确认是屏端读回信息及对应物理屏。不把产品ID、序列号、软件零件号或SoC/BSP版本直接当作所需字段。只有协议或明确字段说明支持时才解析原始字节；不得按猜测拼接。
- 先确认本次故障对象（仪表屏、吸顶屏、中控屏等），再用实际日志的屏幕名称、通路/端口、总线地址及初始化映射核实版本和零件号归属；进程名或行间相邻本身不足以完成屏幕映射。仪表故障找仪表屏信息，吸顶屏故障找吸顶屏信息，不能因为 `ivi_touch` 容易命中而用中控信息代替。映射依据也应保留定位；缺少归属证据时标记目标屏查找失败，必要时向用户核对屏幕/通路映射。
- 在已确认对应故障屏的日志中优先找 `recv_version0` 的完整 `recv data` 行；不同屏可能有其他版本查询标签或协议，按当前屏的实际记录识别。必须提取并报告 `hw_ver`、`sw_ver`、`tp_ver`、`supplier_code` 四项，不能只取软件版本。按输出模板放在“软件/固件版本：”同一行，保留每项原值并附实际日志行号链接；任何缺项明确标记查找失败，不跨屏或跨启动补齐，不猜测另一协议字段的等价关系。
- 屏幕信息应来自与本次故障关联的屏、启动实例或可验证配置；多个候选屏分别标识，不将不同屏的零件号与版本拼在一起。若仅有配置期望值，注明其性质，不充当屏端实际读回值。display_log 尚未获准或无法解码时，说明查找范围限制，但仍按模板输出成功字段或“屏幕信息查找失败”。

## 黑屏、卡屏、红条与局部异常

1. 先区分仪表主 HMI `sva.cluster`、`sva.cluster.safety`、winmgr/screen、vehicle 和中控 Android。分别记录 PID、退出、core、重启及窗口生命周期；不能用 Safety UI 存活证明主 HMI 存活。
2. 建立本次 `物理屏 ↔ disp编号 ↔ DP port ↔ eQdiDisplayId ↔ I²C设备/从地址 ↔ 屏型` 映射。历史仪表曾为 dp3 port1、MAX96781/slave 0x42、/dev/i2c5；只作查找线索，不能套用于新包。
3. 初始化证据查 `init done`、`link stat: 1`、`dp status check pass`、`ser/des ... config succ`、`hotplug reg config succ`。它证明对应链路完成该步骤，不保证后续持续可用或 HMI 资源正常。
4. 背光查 `DCMD_SET_BL`、`backlight onoff`、`backlight_ioctl`、I²C 返回及协议应答；仪表还可能有 4403 控制报文。区分发送意图、主机返回、屏端反馈、物理亮灭。历史 `0x34` 8位与 `0x1a` 7位可能表示同一地址。
5. `0x4c/0xf007`、`diag_panel_training_state`、`Slave failed to ACK` 需先确认对应物理屏及故障前基线。`Control path flush failed`、`MDSS_OSAL_WaitEvent` 需确认显示 ID，不直接归因仪表。
6. 红条/花屏应比较原始 buffer、合成截图、独立硬件层、实体录像、CRC 覆盖区域及内部测试图。系统截图可能漏掉硬件层；FPS 正常不证明像素内容正确；CRC 变化本身不等于错误。
7. 用户明确说明手动重启、测试周期重启不相关时，记录后转查其他方向。主机继续输出不能排除屏端局部掉电；需 MCU/屏端供电、复位、背光使能和 LOCK 波形关联。

## 图形内存不足、HMI 崩溃

- 联查 `Not enough memory`、`size_requested`、`GSL_FAILURE_OUTOFMEM`、`pmem aperture`、`create ... context`、`run fault`、signal、core、窗口删除及新 PID。
- 整机 Free memory、专用 `/mm_dma` 池总剩余、连续/非连续可用量、单次分配需求分别报告，统一字节/KB/MiB单位。不能因整机有空闲排除图形池耗尽，也不能总量不足时只写碎片。
- 查 systeminfo 的完整分进程图形池占用表和相邻采样，记录 PID 变化及启动边界。`kgsl` 统计归属不直接等于 HMI/AVM 客户端归属。
- 占用增长或释放失败是泄漏线索；泄漏需分配/释放账目、buffer 生命周期或可重复趋势。不同 boot 的增长不可相减。
- 同 PID 内存失败后 signal 6 支持相关链，最终 abort 调用点需 core。业务日志停止、进程崩溃、重拉失败分别记录。

## 触摸无响应、鬼点、多指残留、延迟

优先按实际架构追踪：`屏端原始帧 → ads_service/ivi_touch → mtouch → qvm/虚拟输入 → Android InputReader/InputDispatcher → 应用`。每层分别确认最后正常帧和第一处不一致。

- 对齐 touch_num、ID、坐标、PRESS/MOVE/RELEASE、扩展帧、slot/TRACKING_ID、BTN_TOUCH、ACTION_UP/CANCEL 和 pointerCount。
- 原始帧一触点，而主机保存两个同坐标触点时，优先核对解析与状态缓存；不能先认定屏端漏报 release。
- 触点减少后 ID 改变、坐标连续，是重新编号线索；需协议确认 ID 是跨帧稳定身份还是本帧序号。只有协议明确完整快照时才能用“未出现即释放”；增量协议不能这样处理。
- `all finger leave` 文本不替代原始帧及实际发送状态。扩展帧失败、校验错、非法 ID 也不能当零触点帧。
- 只有 Android 日志时结论只到 Android 输入层。QNX DSV_PKMS 未解封不能判定 ads_service 未收/未发。缺事件日志还需核对日志级别与覆盖。
- 延迟按各层同一事件分别量时；不同时钟域先校准，不能直接相减。

## HGSL/HAB 初始化、GSL timeline 超时

- 初始化链路查 `vkCreateInstance`、`gsl_library_open`、`RPC_LIBRARY_OPEN`、`ioctl_hgsl_library_open`、`Failed to open socket -110`、`hab_open_listen`、tombstone 断言。
- 关联同进程主线程、RenderThread 的 native 栈和相同 TID 的内核等待点。单次 ioctl/wchan 不证明死锁；建立等待依赖和持续时间后再描述影响。
- `Invalid dev_id 4294967295`、`Invalid dev handle 0` 可能是失败后的清理打印；核对源码与前置错误，不能单独当根因。
- timeline 链路查 `KSYNC_IOCTL_TIMELINE_WAIT`、`rgs_sync_ioctl`、`RGS_ETIMEDOUT`、`GSL_FAILURE_TIMEOUT`，保留 PID/TID、timeline对象、目标值、实际完成值、超时阈值及返回码。
- errno 110、RGS -5、GSL -10 在历史链路中为逐层转换；具体语义按当前库/代码验证，不能把 RGS -5 当 Linux errno -5。
- seqno/目标值增长不证明完成值推进；收到超时的 HUD/cluster 是调用方，不证明它制造了故障。初始化建通道超时与运行期 timeline 超时分别分析。
- 配对 Host boot、Guest 实例及握手；本次无明确 GPU fault/hang/reset 只表述检查范围，不能因此排除所有 GPU 问题。

## ANR、system_server watchdog、kernfs 与高 CPU

- 无焦点窗口 ANR：分别确认 onResume 回调是否返回、窗口是否建立和获焦、ANR 文件生成与系统最终处理时间。onResume 返回不等于首帧完成。
- ANR 栈抓取失败时，`futex_wait_queue` 与另一线程 `hab_msg_dequeue` 不能自行拼成主线程等待渲染线程；需完整 Java/native 栈及等待对象。
- 查 TGID/PID/TID，避免把 SystemUI、应用和 composer 线程误算成 system_server。
- kernfs 问题区分 R 状态长时间停留的 `sysfs_add_workfn/kernfs_link_sibling`、D 状态 `down_read/down_write` 等待者、pending work；没有 owner 信息不闭合持锁链。
- 查 DMA-BUF `stats` 节点创建/teardown 与对象生命周期。`cnss_diag` 查询节点等待读锁，不证明 CNSS 持写锁；用户态 cnss_diag 和内核 cnss2 work 分开分析。
- CPU 按 TID、多次采样、累计 CPU 时间及 CPU数验证。D 状态阻塞线程与其他满核线程分开查，不能用高 load 解释具体 CPU 热点。
- SIGKILL 发出与 Zygote/退出通知确认的真正死亡时间分开。`SVPRmtOOM` 名称不是 OOM killer 证据。
- 优先补匹配构建的 vmlinux、模块、源码、Guest RAM dump、Java/native 全线程栈和 CPU profile；文本不足以判断 kernfs 树损坏或具体 owner。

## 显示提交超时与 SEA/panic

- 查 suspend/resume、commit done/flush/vblank 超时、`synchronous external abort`、PC/LR、寄存器、Code、完整调用栈及 panic。不同 CRTC/线程的超时不能合并成同一个事务。
- 历史链路为 `_sde_encoder_phys_hyp_wait_for_vblank → sde_hw_ctl_get_flush_register_no_rot → read_reg_vatran → readl_relaxed`；它定位寄存器访问路径，不直接证明 GPU 核心或屏损坏。
- 已知故障指令和寄存器可推 Guest 虚拟读地址；Guest VA、IPA、实际硬件寄存器分别说明。逻辑偏移候选需要匹配反汇编和映射确认。
- 映射、权限、电源、时钟、复位均为待区分项。发生在异常后的 Host 清理/重建不能作为提前撤销的证据；SerDes power 打印也不直接证明 SDE 寄存器电源状态。
